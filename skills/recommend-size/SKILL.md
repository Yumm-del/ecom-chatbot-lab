# 推荐尺码

## 目的

把"商品数据 + 用户数据"变成一句用户能直接行动的建议，**并让用户能验证这个建议**。

## 前置条件

必须同时满足，否则不得调用本 Skill：

1. `lookup-size-chart` 返回 `found: true` 且 `size_chart` 不为 null
2. `clarify-missing-info` 返回 `action: proceed`（身高体重齐全，或用户明确拒绝提供）

## 输入

- 商品尺码表（来自 `lookup-size-chart`）
- `height_cm`、`weight_kg`
- `fit_preference`（tight / regular / loose，默认 regular）
- 用户历史反馈（L3，如"上次 M 太紧"）

## 推算逻辑

### 第一步：从身高体重估算关键围度

用 BMI 区间法给一个**范围**，不给精确值：

```
BMI = weight_kg / (height_m ** 2)
```

| BMI 区间 | 胸围参考 | 腰围参考 |
|---|---|---|
| < 18.5 | 身高对应基准 -4cm | 基准 -3cm |
| 18.5–22.9 | 基准 | 基准 |
| 23–26 | 基准 +5cm | 基准 +5cm |
| > 26 | 基准 +9cm | 基准 +9cm |

> ⚠️ 这是**粗略估算**，必须向用户说明"这是按平均体型估算的区间"。
> 不要把它包装成精确测量。

### 第二步：按商品属性修正

| 商品属性 | 修正规则 |
|---|---|
| `fit_type: slim` | 按估算围度 +2~4cm 选码（否则会太紧） |
| `fit_type: loose` / `oversized` | 按估算围度选，不要加大（本来就宽） |
| `stretch: high` | 允许按估算值选，不上浮 |
| `stretch: none` | 留 2cm 余量 |
| `notes` 有"偏大/选小一码" | **以 notes 为准，覆盖上面的规则** |

### 第零步（优先级最高）：先看卖家备注有没有「强指引」

如果商品 `notes` 里出现这类表述，按下表处理：

| 备注写法 | 处理方式 |
|---|---|
| "按腰围选码最准""以腰围为准" | 优先用腰围判断；有腰围数据直接用；没有则给估算，**并明确说明"建议量一下腰围"** |
| "按脚长选""脚背高选大一码" | 同上，以脚长为准 |
| "肩线偏窄，肩宽超 40 建议大一码" | 先问肩宽，或把肩宽作为主要依据 |
| "版型偏大，建议选小一码" | 直接按其规则调整，不需要问 |

**硬约束 1**：强指引存在时，BMI 估算只能作为辅助，**不能作为唯一依据**——回复里必须点明"这件商品按 X 选码最准"。

**硬约束 2**：出现以下情况时，**必须真的问一次该维度**，不能只给估算：

- 用户自述体型刚发生变化（"我最近胖了十斤""瘦了"）
- 用户的身高体重明显偏离平均体型
- 用户此前没有该维度的任何数据

> 这是 v2 评测里发现的真实缺陷（D02 用例）：卖家备注写"腰部无松紧，按腰围选码最准"，
> 用户又说自己胖了十斤——估算基准已经变了，v2 却还用 BMI 推了个"腰围约 74–75cm"直接给码。
> **备注是卖家对这件衣服的经验，BMI 是对人群的统计；当用户自己的数据刚变过，两个都不能当准。**

### 第三步：优先使用历史反馈

如果 L3 里有同品类同品牌的反馈：

- "上次 M 太紧" → 本次建议 L
- "上次 L 太大" → 本次建议 M

**历史反馈的权重高于 BMI 估算**，因为它是真实结果。

## 输出格式

必须包含三部分，缺一不可：

```
【建议】M 码
【依据】这款连衣裙 M 码胸围 88cm、腰围 70cm，腰头无松紧。按您 165cm / 60kg 估算，
        胸围约在 88–90cm 区间，M 码贴合，L 码会更宽松。
【风险】这是按平均体型估算的。如果您肩比较宽或上身偏丰满，建议 L。
```

**为什么必须有"依据"和"风险"？**
因为用户真正需要的不是一个答案，是**能自己判断这个答案靠不靠谱的信息**。
只给结论的 AI，答错了用户毫无防备。

### 输出格式的硬约束：估算值必须标注

凡是**不是从商品表或用户口中直接得到**的数，一律要带"约 / 大概 / 估算 / 区间"字样。

| ❌ 错误写法 | ✅ 正确写法 |
|---|---|
| 您胸围 88cm | 您的胸围**约** 88cm（按身高体重估算） |
| 腰围 74cm | 腰围**大概在** 74–75cm **区间** |
| 按您的 BMI 23.9 | 按身高体重**粗算**，BMI 约 23.9 |

> 这条也是 v2 的真实缺陷：D01 用例里 v2 输出了"胸围约 88cm"，但**"约"字是模型偶然加的，不是规则强制的**。
> 同一个位置换个商品就可能写成确定值，用户会当成实测数据来做决策。

## 关键规则

### 规则 1：必须给出可验证的依据

不能说"我觉得 M 合适"，必须说"因为 M 码胸围 88cm，而您的估算胸围约 88–90cm"。

### 规则 2：必须说明不确定性

任何基于估算的建议，都要带一句风险提示。**这不是免责声明，是让用户参与决策。**

### 规则 3：用户偏好优先于标准建议

`fit_preference: loose` 的用户，即使标准建议是 M，也要说"按您喜欢的宽松感，建议 L"。

### 规则 4：不要在尺码建议里夹带推销

"建议 M 码，另外我们还有一款…"——这会让用户怀疑建议的动机。
**尺码建议必须是纯技术回答。**

## 失败处理

- 估算出的围度正好落在两码之间 → 给两个选项，说明差异（"M 贴身、L 宽松"），让用户选。
- 用户体型明显偏离 BMI 表（如身高 150cm / 80kg） → 说明"按平均体型估算可能不准"，建议实测或问卖家。
- 商品是鞋类 → 用脚长而不是身高体重，此时应改问脚长。
