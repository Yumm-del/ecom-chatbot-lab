# 查询尺码表

## 目的

把"可查的事实"和"可做的判断"硬性分开。

**这是本项目最重要的一条规则**：商品尺寸是事实，只能来自数据；"你该穿 M"是判断，可以由模型做。

公开 badcase BC-01 之所以发生：AI 把 **80/90** 这个规格答成"最大的"，
而 80/90 是**每公斤的只数**——数字越大，单只虾越小。它拿到了字段，却按"数字越大越好"猜了方向。

## 输入

- `product_id`：商品 ID

## 输出

读取 `data/products.json`，返回该商品的结构化字段：

```json
{
  "found": true,
  "product_id": "p_003",
  "fit_type": "regular",
  "stretch": "none",
  "material": "100% 聚酯纤维",
  "size_chart": {
    "unit": "cm",
    "columns": ["chest", "waist", "hip", "length"],
    "rows": {"S": [84, 66, 90, 105], "M": [88, 70, 94, 107]}
  },
  "notes": "腰部无松紧，按腰围选码最准。"
}
```

## 关键规则

### 规则 1：禁止推断尺寸

**不允许**出现以下行为：

- ❌ "这类商品一般 M 码胸围 90cm 左右"
- ❌ "根据经验，您穿 L 应该差不多"
- ❌ 用其他商品的尺码表代替

**允许**的只有：把 `size_chart` 里的数字原样引用出来。

### 规则 2：数据缺失时，唯一的正确回答是"查不到"

当 `size_chart` 为 `null` 时，必须：

1. 明确说明该商品没有尺码表，并给出 `chart_missing_reason`（如果有）；
2. 建议用户联系卖家或看商品页；
3. 触发 `escalate-to-human`。

**不允许**任何形式的估计。哪怕用户说"你就估一个"，也只能给"如何自己量的方法"，不能给具体码数。

### 规则 3：注意"反向语义"字段

商品的 `notes` 字段里可能包含与直觉相反的信息，必须逐字读完再回答。例如：

- 衬衫写"版型偏大，建议选小一码" → 不能按标准版型推
- 卫衣写"本身就是 oversize，按正常码选即可" → 不能建议加大
- 打底衫写"胸围为平铺未拉伸值，可拉伸约 15cm" → 不能直接用平铺值比较

> **BC-01 的教训**：规格编号的方向可能和直觉相反。80/90 是每公斤的只数，数字越大虾反而越小。
> 所以**读到字段不等于读懂字段**——涉及商品属性的回答，不仅要取到值，还要确认这个值的**单位和方向**。

## 失败处理

| 情况 | 处理 |
|---|---|
| `product_id` 不存在 | 返回 `{"found": false}`，转 `escalate-to-human` |
| `size_chart` 为 null | 见规则 2 |
| 用户问的是商品表里没有的字段（如"这件会不会起球"） | 说明数据里没有，不推测 |

## 自检清单

回答前必须确认：

- [ ] 我引用的每个数字，都能在 `products.json` 里找到对应字段
- [ ] 我没有用"一般""通常""大概"来描述任何尺寸
- [ ] 我读完了 `notes` 再下结论
