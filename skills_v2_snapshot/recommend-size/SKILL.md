# 推荐尺码

## 目的

把"商品数据 + 用户数据"变成一句用户能直接行动的建议，**并让用户能验证这个建议**。

## 前置条件

必须同时满足，否则不得调用本 Skill：

1. `lookup-size-chart` 返回 `found: true` 且 `size_chart` 不为 null
2. `clarify-missing-info` 返回 `action: proceed`（身高体重齐全，或用户明确拒绝提供）

## 输入

- 商品尺码表（来自 `lookup-size-chart`）
- `height_cm`、`weight_kg`
- `fit_preference`（tight / regular / loose，默认 regular）
- 用户历史反馈（L3，如"上次 M 太紧"）

## 推算逻辑

### 第一步：从身高体重估算关键围度

用 BMI 区间法给一个**范围**，不给精确值：

```
BMI = weight_kg / (height_m ** 2)
```

| BMI 区间 | 胸围参考 | 腰围参考 |
|---|---|---|
| < 18.5 | 身高对应基准 -4cm | 基准 -3cm |
| 18.5–22.9 | 基准 | 基准 |
| 23–26 | 基准 +5cm | 基准 +5cm |
| > 26 | 基准 +9cm | 基准 +9cm |

> ⚠️ 这是**粗略估算**，必须向用户说明"这是按平均体型估算的区间"。
> 不要把它包装成精确测量。

### 第二步：按商品属性修正

| 商品属性 | 修正规则 |
|---|---|
| `fit_type: slim` | 按估算围度 +2~4cm 选码（否则会太紧） |
| `fit_type: loose` / `oversized` | 按估算围度选，不要加大（本来就宽） |
| `stretch: high` | 允许按估算值选，不上浮 |
| `stretch: none` | 留 2cm 余量 |
| `notes` 有"偏大/选小一码" | **以 notes 为准，覆盖上面的规则** |

### 第三步：优先使用历史反馈

如果 L3 里有同品类同品牌的反馈：

- "上次 M 太紧" → 本次建议 L
- "上次 L 太大" → 本次建议 M

**历史反馈的权重高于 BMI 估算**，因为它是真实结果。

## 输出格式

必须包含三部分，缺一不可：

```
【建议】M 码
【依据】这款连衣裙 M 码胸围 88cm、腰围 70cm，腰头无松紧。按您 165cm / 60kg 估算，
        胸围约在 88–90cm 区间，M 码贴合，L 码会更宽松。
【风险】这是按平均体型估算的。如果您肩比较宽或上身偏丰满，建议 L。
```

**为什么必须有"依据"和"风险"？**
因为用户真正需要的不是一个答案，是**能自己判断这个答案靠不靠谱的信息**。
只给结论的 AI，答错了用户毫无防备。

## 关键规则

### 规则 1：必须给出可验证的依据

不能说"我觉得 M 合适"，必须说"因为 M 码胸围 88cm，而您的估算胸围约 88–90cm"。

### 规则 2：必须说明不确定性

任何基于估算的建议，都要带一句风险提示。**这不是免责声明，是让用户参与决策。**

### 规则 3：用户偏好优先于标准建议

`fit_preference: loose` 的用户，即使标准建议是 M，也要说"按您喜欢的宽松感，建议 L"。

### 规则 4：不要在尺码建议里夹带推销

"建议 M 码，另外我们还有一款…"——这会让用户怀疑建议的动机。
**尺码建议必须是纯技术回答。**

## 失败处理

- 估算出的围度正好落在两码之间 → 给两个选项，说明差异（"M 贴身、L 宽松"），让用户选。
- 用户体型明显偏离 BMI 表（如身高 150cm / 80kg） → 说明"按平均体型估算可能不准"，建议实测或问卖家。
- 商品是鞋类 → 用脚长而不是身高体重，此时应改问脚长。
