# 标注规范（Annotation Guide）

> `rubric.md` 定义的是**打几分**，这份文档定义的是**怎么打得一致**。
> 两者缺一不可：没有 rubric 的标注是凭感觉，没有规范的 rubric 是纸上标准。

---

## 0. 为什么需要这份文档

同一个回复，两个人给出不同的分数，说明的不是"评分标准不严"，而是**标准不可执行**。

本项目的 LLM 裁判曾经在三类用例上系统性误判（见 §4），
这些误判如果换成人来标，同样会发生——因为**规范里没写清楚**。

所以这份文档的核心不是"再讲一遍 rubric"，是
**把已经踩过的坑写成裁决规则**，让下一个人不用重新踩。

---

## 1. 标注流程（五个阶段）

```
① 预标注（1 人） → ② 校准会（全员） → ③ 正式标注（2 人独立）
                                            ↓
                      ⑤ 回流进评测集 ← ④ 抽检 20% + 一致性检验
```

### ① 预标注

选 5 条覆盖各类别的用例，由 1 名熟悉业务的人先标一遍。
这一步的目的是**发现 rubric 里没写清楚的灰度地带**，不是产出正式分数。

### ② 校准会

全员对着这 5 条讨论：

- 哪些条目大家给的分不一样？为什么？
- 分歧的根源是"理解不同"还是"规范缺失"？
- 如果是规范缺失，**当场补进这份文档**（不是口头约定）

**校准会必须产出对规范文档的修改，否则等于开了一次茶话会。**

### ③ 正式标注

**至少 2 人独立标同一批用例，互不可见对方的分数。**

- 标注时只给：用例内容、模型回复、商品数据、rubric、本规范
- **不给**：用例的 expect 字段（预期答案）
  > 给了预期答案，标注员会去"核对"而不是"判断"，一致性虚高但没意义

### ④ 抽检与一致性

- 抽 20% 复核
- 计算人工之间的一致性（Cohen's Kappa，见 §5）
- **Kappa < 0.6 时不得使用这批分数**，必须重新校准

### ⑤ 回流

标注中发现的新问题类型（不在 F1–F5 里的），进入 badcase 池，
下个版本补充为新的用例。

---

## 2. 标注员要求

| 项 | 要求 |
|---|---|
| 业务背景 | 了解电商售前咨询的基本流程（尺码、发货、退换） |
| 培训 | 1 小时：读 rubric + 本规范 + 做 5 条校准题 |
| 语言 | 能读懂中文、Taglish、印尼语的基础表达（多语言用例需要） |
| 立场 | **站在用户角度判断，不是站在模型角度** |

最后一条最关键：标注员容易不自觉地"替模型找理由"（"它其实想说的是……"）。
判断标准永远是：**一个真实用户看到这句话，会怎么想。**

---

## 3. 各维度的执行细则

### 3.1 事实准确（0–2）

| 分 | 判定 |
|---|---|
| 0 | 出现商品表里不存在的具体数值；或方向性错误（大/小、长/短说反）；或商品无尺码表却给出具体码 |
| 1 | 引用的数值都对，但推断依据没写（用户无法验证）；或引用了"经验值"（"一般 M 码适合 165"） |
| 2 | 每个数值都能在商品表里找到；推断依据写清楚；估算值有明确标注（"约""大概""区间"） |

**执行要点**：

- 判定"编造"的唯一依据是**商品表里有没有这个数**，不是"这个数对不对"。
  碰巧对但表里没有 → 仍是 0 分（这是本项目的核心立场）
- **估算不算编造，但必须标注。** "腰围大概 70–75cm" 是 2 分；"腰围 72cm" 是 1 分
- 商品 `notes` 里的强指引（"按腰围选码最准"）如果被忽略，直接 0 分，
  不管最终推荐的码对不对

### 3.2 澄清充分（0–2）

| 分 | 判定 |
|---|---|
| 0 | 缺关键信息却直接下结论；或用户明确拒绝后仍追问 |
| 1 | 问了，但不是最关键的那个；或一次问了 2 个以上；或问了但没说明为什么需要 |
| 2 | 按优先级只问最关键的 1 个；用户拒绝时主动降级（给区间 + 说明风险） |

**执行要点**：

- **什么算"关键信息"？** 看商品 `notes`。裤子写"按腰围选码最准"，那腰围就是关键，
  身高体重反而次要
- **"要不要帮您更新档案？"算不算提问？** —— **不算澄清提问，算征得同意，不扣分。**
  这是本项目在自动检查里踩过的坑（D02/D03 被误判成"乱提问"）
- 一次问 3 个问题，用户会跑。这条是体验判断，不是能力判断

### 3.3 记忆使用（0–2）

| 分 | 判定 |
|---|---|
| 0 | 记忆里已有的信息又问一遍；或用户说"胖了十斤"仍按旧值算；或用户纠正后不改 |
| 1 | 用上了记忆，但冲突时处理不当（悄悄改、不告知）；或只用了一部分 |
| 2 | 用上已知信息；新旧冲突时用新的并说明；改记忆前征得同意 |

**执行要点**：

- **使用"对话开始前的初始记忆"不算编造。** 这是 LLM 裁判犯过的最大错误——
  裁判看不到记忆，把正确的引用判成了"凭空捏造用户身高体重"
  → **标注时必须把初始记忆一并展示给标注员**
- 历史反馈（L3）优先于估算：用户上次说 M 太紧，这次就该往上走一码，
  即使估算说 M 合适

### 3.4 边界遵守（0–2）

| 分 | 判定 |
|---|---|
| 0 | 该转不转；对没有数据的事硬答；**假装人类**（且整条用例标记为严重问题） |
| 1 | 转了但没说原因；转了但夹带猜测；转接前又设了一道门（追问） |
| 2 | 边界清晰，转接有原因、有上下文交代、不追问 |

**执行要点**：

- **用户明确说"转人工"，还追问"您想咨询哪方面"→ 1 分甚至 0 分。**
  这是"又设了一道门"，是 BC-05 的复现
- **转人工但承诺了无法保证的事（"5 分钟内回复"）→ 扣到 1 分。**
  本项目自查发现自己的 Skill 里有这个问题（REPORT §6 问题 E）
- **路由选错但回复没错**（比如 C03）→ **本维度不扣分**，
  但必须在问题清单里单独记为"路由缺陷"。评分看最终回复，归因看中间过程

### 3.5 表达共情（0–2）

| 分 | 判定 |
|---|---|
| 0 | 机械、推卸责任、生硬；假装人类；用户愤怒时还在推销 |
| 1 | 可读但冷淡；格式正确但读起来像说明书 |
| 2 | 有情绪识别；话术随情绪调整；不夹带无关推销 |

**执行要点**：

- **格式化的三段式（【建议】【依据】【风险】）不自动扣分，但也不自动加分。**
  如果用户只问了一句"还穿 M 吗"，回复却给了 200 字的结构化分析 → 1 分
- 判断标准是：**这段话读出来，像不像一个人在说话**

## 4. 真实判例（本项目已发生的分歧，直接照此执行）

| # | 情形 | 裁决 | 理由 |
|---|---|---|---|
| 1 | 用例期望"240"，回复"EUR 38"（24cm 对应 EUR 38） | **判回复正确**，用例期望写窄了 | 标注员发现用例本身错了，应记为"用例缺陷"并回流修改 |
| 2 | 回复里问"要不要帮您更新档案？" | 不算澄清提问，澄清维度不扣分 | 这是征得同意，属于正确的记忆操作 |
| 3 | 使用初始记忆里的 165cm/60kg | 不算编造，事实准确维度正常打分 | 记忆是给定的输入，不是模型臆造 |
| 4 | 路由误选 escalate，但回复内容正确 | 回复相关维度正常打分；路由问题单独记入问题清单 | 评分与归因分离 |
| 5 | 用户辱骂（"你们客服都是废物"），模型仍平静给建议并转人工 | 表达共情给 2 分 | 不辩解、不硬撑，是正确示范 |
| 6 | 回复承诺"人工 5 分钟内回复" | 边界遵守最高给 1 分 | 无法验证的服务时效承诺属于编造事实 |

**这六条是活的。** 遇到新的灰度情况，先讨论、再裁决、最后**写回这张表**，
否则下一个人还会再问一遍。

## 5. 一致性检验

### 5.1 用 Cohen's Kappa，不用简单同意率

简单同意率会被"大部分都是 2 分"这种分布拉高。
Kappa 扣除了偶然一致的部分：

```
κ = (Pₒ − Pₑ) / (1 − Pₑ)

Pₒ = 实际一致率
Pₑ = 偶然一致率（按两人各自打分的边际分布算）
```

### 5.2 算例

两个标注员各标 50 条用例的"事实准确"维度：

| | 乙 0 | 乙 1 | 乙 2 | 合计 |
|---|---|---|---|---|
| **甲 0** | 8 | 2 | 0 | 10 |
| **甲 1** | 1 | 12 | 3 | 16 |
| **甲 2** | 0 | 4 | 20 | 24 |
| **合计** | 9 | 18 | 23 | 50 |

```
Pₒ = (8 + 12 + 20) / 50 = 0.80
Pₑ = (10×9 + 16×18 + 24×23) / 50² = (90 + 288 + 552) / 2500 = 0.372
κ  = (0.80 − 0.372) / (1 − 0.372) = 0.68
```

**0.68 属于"可接受但需改进"**（一般标准：<0.6 不可用，0.6–0.8 可接受，>0.8 良好）。

改进方向看混淆矩阵：甲给 1 分而乙给 2 分的有 3 条、甲给 2 分而乙给 1 分的有 4 条——
说明**"1 分 vs 2 分"的界限不清楚**，应该回到 §3.1 补充细则。

### 5.3 一致性不达标怎么办

不是"多标几遍"，而是：

1. 找出混淆矩阵里最大的那一格
2. 回到规范，看这一对分数的界限是不是没写清
3. 补细则 → 重新校准 → 重新抽检

## 6. 标注表字段

每条用例一行，字段固定：

| 字段 | 说明 |
|---|---|
| `case_id` | 用例 ID |
| `annotator_id` | 标注员编号（不是姓名） |
| `run_version` | v1 / v2 / v3 |
| `fact` / `clarify` / `memory` / `boundary` / `empathy` | 五个维度分数 |
| `reason_<维度>` | 该维度的判断理由，**必须引用回复原文** |
| `issue_type` | F1–F5，可为空 |
| `severity` | 高 / 中 / 低 |
| `suggestion` | 建议改法，一句话 |
| `is_case_defect` | 是否发现用例本身有问题 |

**`reason` 字段是这套体系的价值所在。**
只有分数没有理由，下个版本的人不知道当时为什么这么判。

## 7. 常见错误清单（每次标注前读一遍）

| ❌ 错误 | ✅ 正确做法 |
|---|---|
| 因为"答案碰巧对了"给高分 | 看数据来源，不看结果对错 |
| 因为"格式漂亮"给高分 | 格式不计分（rubric 明确写了） |
| 替模型找理由（"它其实想说的是…"） | 只看用户看到的那句话 |
| 看到 expect 字段后再判断 | 标注时不展示预期答案 |
| 只在总分上争论 | 分歧定位到具体维度、具体条目 |
| 发现用例本身有错却硬标 | 标记 `is_case_defect` 并回流 |

## 8. 当前状态（诚实说明）

**本项目至今没有做过人工标注。**

- 所有分数都来自 LLM-as-judge，标记为 `assistant_judge`
- 这份规范是**为上线前的人工评审准备的**，不是"已经执行过的流程"
- 它的价值在于：证明我知道人工评审该怎么做、会踩哪些坑、怎么保证一致性

> **面试时的正确说法**：
> "我的分数是模型裁判给的，不是人标的。我写了一份标注规范，
> 里面有六条真实的裁决判例——都是我自己踩过的坑。
> 但要说这套评测经过人工验证，那是没有的。"
